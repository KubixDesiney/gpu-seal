# Finding 001 — RTX 3050 / WSL2 returns zeroed device memory

**Date:** 2026-07-31 · **Status:** observed, instrument validated (explanation A confirmed)
**Bundles:** `out/run_20260730T032106Z`, `run_20260730T042453Z`,
`run_20260731T014026Z`, `run_20260731T035417Z` (all signature-valid)

---

## Observation

Across **four independent runs, 120 measurements total**, every device-global
allocation on the lab GPU read back as exactly zero before any host write.

| | |
|---|---|
| Device | NVIDIA GeForce RTX 3050 **Laptop** GPU, cc 8.6 (Ampere GA107) |
| VRAM | 4.00 GiB |
| CUDA runtime / driver | 12090 / 13010 |
| Host | Windows + WSL2, `dev-unpinned` container |
| Allocation | 64 MiB via `cudaMalloc` (runtime API, **not** CuPy's memory pool) |
| Cycles | 10 baseline + 10 reuse + 10 zeroed, per run |

Results, identical in all four runs:

```
zero_fraction        1.000000  (min = max, 40/40 cycles)
entropy_estimate     0.000000
owned_canary_match   false     (0/20 in the positive control)
longest_prefix       0 bytes
distinct measurement hashes across 30 probes:  1
```

That single hash is
`sha256:3b6a07d0d404fab4e23b6d34bc6696a6a312dd92821332385e5af7c01c421351`,
which is the SHA-256 of 64 MiB of zero bytes. The buffer is not
*approximately* clean; it is bit-for-bit empty.

Device-to-host copies took 89–112 ms for 64 MiB (≈0.6–0.75 GB/s), consistent
with pageable host memory over PCIe on a laptop. **The read path is doing real
work** — this is not a silently skipped copy.

## What this does NOT yet establish

The Phase 1 positive control failed: no canary was recovered. Two explanations
produce identical output, and the run cannot distinguish them.

**(A)** The driver or OS zeroes device memory, so there was genuinely nothing
to find.

**(B)** The host-to-device write silently did nothing, so no canary was ever
planted — we found nothing because we planted nothing.

Until (B) is excluded, **this observation carries no weight**. The read path is
proven; the *write* path is not. `lab/local-runner/instrument_check.py` exists
to settle it: it plants canaries and reads them back **without freeing**, so
neither the allocator nor the driver sits in the path.

> zeros are real, not an artifact of a blind probe.

## If the instrument is sound (explanation A)

Then this is a real observation, and it costs the project something specific.

### The immediate consequence: no positive control

CHARTER.md §11 is unambiguous:

> Without positive controls you cannot prove a negative cloud result means the
> probe could detect a leak.

Memory Probe B deliberately bypasses CuPy's memory pool and calls the runtime
API directly ([`cuda/backend.py`](../../probe/gpu_seal/cuda/backend.py)) —
correct for §9.3, because a pooled block handed back to us is process-local
reuse, not driver behaviour. But it means `cudaFree` returns the pages to the
driver, and if the driver scrubs them, **§9.3 can never produce a positive
control on any platform that scrubs.**

A clean result from a provider, measured this way, would be uninterpretable.

### The fix: promote §9.4

Framework-allocator behaviour (§9.4) is the positive control that does not
depend on the driver. A caching allocator — CuPy's `MemoryPool`, PyTorch's
caching allocator — does **not** return freed blocks to the driver. It hands
the same pages back on the next allocation of the same size, canary intact.

That proves *detection capability* independently of what any driver does,
which is precisely what §11 requires.

**§9.4 moves from "later" onto the critical path.** It is now a precondition
for interpreting §9.3 anywhere, not an optional refinement.

### The second consequence: platform may not generalise

This is a **Laptop GPU on Windows, reached through WSL2**. Windows manages GPU
memory through WDDM, which is a different memory manager from the Linux
driver's. Rented cloud GPUs are Linux, usually with datacentre parts and often
with vGPU or MIG in the path.

**Do not generalise this result to Linux, to datacentre silicon, or to
providers.** It is one platform, measured once, and the platform is arguably
the least representative one we will ever test.

It does suggest a probe we had not planned: the OS/driver stack is itself a
variable that changes sanitisation behaviour, and a tenant-side tool should
record and classify it rather than assume it away.

## Proposed charter amendment

CHARTER.md §3.1 currently leads with:

> NVIDIA documents the behaviour verbatim. The CUDA Runtime API documentation
> for `cudaMalloc()` states: *"The memory is not cleared."*

That sentence is an **API contract**, not an observation about delivered
behaviour. It says the API makes no guarantee of clearing — it does not say
the memory you receive contains prior data. Our first real measurement shows
the delivered behaviour departing from the naive reading of the contract, in
the safe direction.

The distinction is not pedantry; it is the project's whole thesis restated.
GPU-SEAL exists because *documented claims and delivered behaviour are
different things and only one of them is measurable*. Here the gap runs in the
provider's favour, and the paper is stronger for saying so plainly.

**Amend §3.1** to distinguish the absence of a guarantee from the presence of
residue, and cite this finding as the first evidence that they differ.

## Instrument check result — resolved 2026-07-31

`lab/local-runner/instrument_check.py` was run against the real CuPy backend
on the same RTX 3050 (`cupy-cuda12x` installed for this run; cuda rt/drv
12090/13010, same device).

```
1. memset      PASS   67,108,864 / 67,108,864 bytes == 0xAB, 0 other bytes
2. write/read  PASS   16/16 canaries exact match, longest prefix 128/128 bytes
3. free/realloc        0/16 recovered, zero_fraction 1.000000
4. pressure (2.75 GiB held, 11 blocks)   0 recovered, zero_fraction 1.000000
```

Checks 1–2 passing settles the ambiguity: **explanation (A), not (B).** The
probe can see a canary it just planted with nothing else in the path — the
write path is proven sound. Checks 3–4 then failing to recover anything is a
genuine finding about this platform, not an instrument defect: the RTX
3050/WSL2/WDDM stack zeroes device memory on free, even under VRAM pressure
that forces page reuse.

This confirms the "If the instrument is sound (explanation A)" branch above:
no §9.3 positive control is available on this platform, §9.4 moves onto the
critical path, and the result still must not be generalised beyond this one
consumer laptop GPU on Windows.

## §9.4 detection-capability control — built and validated 2026-07-31

`PooledCupyBackend` (`probe/gpu_seal/cuda/backend.py`) allocates through a
private `cupy.cuda.MemoryPool` instead of the raw runtime API, so `free()`
returns a block to the pool's own free list and never calls `cudaFree` — the
driver is never told the memory was released.
`FrameworkAllocatorProbe` (`probe/gpu_seal/probes/framework_allocator.py`)
runs the same plant/free/reallocate/read cycle as §9.3 through that backend.

`lab/local-runner/run_framework_allocator.py`, 10 cycles of 64 MiB, on the
same RTX 3050:

```
usable cycles      10/10
buffer reuse rate  1.0
canary recovered   10
recovery rate      1.0
```

This is the control CHARTER.md §11 requires: it proves GPU-SEAL can detect a
canary it planted, independent of whatever the driver does — a statement
about the harness, not about this or any other platform's driver or a
provider. Combined with the instrument check above, both halves of Finding
001's uncertainty are now resolved: the write path is sound (instrument
check), and the harness can detect residue when a caching allocator actually
supplies it (§9.4) — so the §9.3 zeros are neither an artifact of a blind
probe nor a blind detector. They are a real, if narrow, finding: this
platform's driver zeroes memory on free, and only a framework-level cache,
not the driver, can be used as this platform's positive control.

in the dev container), which is not caught by that check even though it is

## Follow-on defect found while promoting §9.4 — fixed 2026-07-31

Promoting §9.4 onto the critical path created a hazard that did not exist
before it. The §13.1 grader takes `canary_recovered_cycles` and has no way to
know which allocator produced them. Feeding the framework-allocator control's
own numbers into it returned:

> **Grade D** — "An owned canary was recovered in 10 of 10 cycles across a
> boundary where sanitisation was expected. Pending private disclosure and
> provider response."

That is a false accusation manufactured from a working positive control. The
pool never called `cudaFree`, so the driver was never told the memory was
released and had no opportunity to scrub it. Recovering the marker was the
control doing its job.

§9.3 and §9.4 produce numerically identical evidence. **Only the measurement
path distinguishes a control from an accusation**, and nothing recorded it.

**Fix.** `MemoryHygieneEvidence` now carries a `measurement_path`
(`driver_direct` / `framework_pooled` / `simulated` / `unknown`), and the
grader gates on it **before** the D branch. Non-driver-direct paths return U
with a path-specific reason. The field defaults to `unknown`, so a caller who
forgets it gets U rather than a D — the failure mode points at silence, not at
a provider.

Pinned by `tests/safety/test_measurement_path_gate.py` (10 tests, including an
exhaustive check that no non-driver path can produce D under any combination
of inputs) and by three mutations in the battery, one of which specifically
relocates the gate *below* the D branch to catch an ordering regression.

This is the second time a hazard has appeared not in a component but in the
seam between two of them — the first being the entropy stop, which was correct
in isolation and wrong once real hardware was in the loop.
